# Utilities and Data Structures

This is the honest answer to "what are the data structures in this
codebase": there are almost none, because there is no runtime data. This
doc covers the one real utility function that exists (`cn()`), and
catalogs every meaningful TypeScript type used across the app — which is
the closest analogue to "data structures" a static-content site like this
one has.

## `lib/utils.ts` — the `cn()` class-name merger

```ts
import { clsx, type ClassValue } from "clsx"
import { twMerge } from "tailwind-merge"

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs))
}
```

This is the standard shadcn/ui utility function, generated by the shadcn
CLI init step (matching the `"utils": "@/lib/utils"` alias in
`components.json`). It composes two libraries:

1. **`clsx(inputs)`** — takes any number of arguments of type `ClassValue`
   (a string, a number, `null`/`undefined`/`false` (ignored), an array of
   `ClassValue`, or an object map like `{ "font-bold": isActive }` where
   only keys with truthy values are kept) and flattens them into a single
   space-separated class string. This is what lets you write conditional
   classes like `cn("btn", isPrimary && "btn-primary", { "btn-disabled":
   disabled })` instead of manually building a template string with
   ternaries.
2. **`twMerge(...)`** — takes clsx's output string and resolves
   **Tailwind-specific conflicts** by recognizing Tailwind's utility-class
   naming scheme. E.g. `twMerge("p-2 p-4")` returns `"p-4"` — it knows
   both classes set the same CSS property (`padding`) and keeps only the
   last one, rather than emitting a string where the CSS cascade order
   (not the coder's intent) decides which one visually wins.

The type import `type ClassValue` (from `clsx`) is TypeScript's
`import type` syntax — it imports only the *type*, guaranteed to be
erased at compile time with zero runtime footprint (as opposed to a
regular `import { ClassValue }`, which would attempt to import a real
JS binding and fail here, since `ClassValue` is a TS-only type, not an
exported value).

**This function is currently unused.** No `.tsx` file anywhere in `app/`
imports `cn` from `@/lib/utils`. Every component in this repo applies a
*single*, static CSS Modules class per element (`className={styles.foo}`)
— there is no conditional class logic anywhere in the app, so there has
been no occasion to need a merge utility yet. It exists purely as
leftover shadcn/ui scaffolding (see
[`07-dependencies-audit.md`](./07-dependencies-audit.md)). If you start
writing a component with conditional styling (e.g. an active nav-link
state, a disabled button variant), this is the correct existing utility to
reach for rather than hand-rolling template-string class concatenation.

## TypeScript types used throughout the app

None of these are custom `interface`/`type` declarations authored in this
repo — every single one is imported from `next`'s own type definitions
(or React's). Listing them here because understanding their *shape* is
what makes the rest of this documentation set (especially
[`05-metadata-and-seo.md`](./05-metadata-and-seo.md)) legible without
cross-referencing Next's source.

| Type | Imported from | Used in | Shape (relevant fields only) |
|---|---|---|---|
| `Metadata` | `next` | Every `page.tsx`/`layout.tsx` that exports `metadata` | `{ title?, description?, keywords?, openGraph?, twitter?, robots?, alternates?, metadataBase?, authors?, icons? }` — every field optional, deeply nested (e.g. `openGraph.images` is `string[] \| OGImage[]`) |
| `Viewport` | `next` | `app/layout.tsx` | `{ width?, initialScale?, ... }` — separated from `Metadata` in modern Next versions specifically because viewport/theme-color used to live under `metadata.viewport` and was split into its own export for tree-shaking/caching reasons upstream |
| `MetadataRoute.Sitemap` | `next` | `app/sitemap.ts` | `Array<{ url: string, lastModified?: string \| Date, changeFrequency?: "always" | "hourly" | "daily" | "weekly" | "monthly" | "yearly" | "never", priority?: number }>` |
| `MetadataRoute.Robots` | `next` | `app/robots.ts` | `{ rules: { userAgent?: string \| string[], allow?: string \| string[], disallow?: string \| string[] } \| Array<...>, sitemap?: string \| string[], host?: string }` |
| `MetadataRoute.Manifest` | `next` | `app/manifest.ts` | Mirrors the W3C Web App Manifest spec: `{ name, short_name, description, start_url, display, background_color, theme_color, icons: Array<{ src, sizes, type }> }` |
| `NextConfig` | `next` | `next.config.ts` | `{ turbopack?: { root?: string }, ... }` — a large optional-everything config object; this repo only sets `turbopack.root` |
| `ClassValue` | `clsx` | `lib/utils.ts` | `string \| number \| boolean \| undefined \| null \| ClassValue[] \| { [key: string]: unknown }` — a recursive union type, which is why it can represent arbitrarily nested conditional class expressions |
| `React.ReactNode` | `react` | `app/layout.tsx` (`{ children }: { children: React.ReactNode }`) | The universal "anything React can render" union: `ReactElement \| string \| number \| Iterable<ReactNode> \| boolean \| null \| undefined` |

## Why there are no custom data models

Every page's content — prices, service descriptions, legal clauses, team
copy — is authored as literal JSX text/attribute values directly inside
each `page.tsx`. There is no:
- `type Service = { title: string; description: string; icon: string }`
  interface with an array of services mapped to JSX (the 3 service cards
  in `app/serviceComponent/service.tsx` and the 3 pricing tiers in
  `app/pricing/page.tsx` are each hand-duplicated JSX blocks instead — see
  [`02-routing-and-pages.md`](./02-routing-and-pages.md) and
  [`03-components.md`](./03-components.md) for the specific instances).
- Fetched or persisted content of any kind (no `fetch`, no ORM, no
  `.json`/`.md` content files parsed at build time via something like
  `gray-matter` or `contentlayer`).
- Shared constants file for repeated values — the contact email
  (`contact@savepoint.cc`) and Facebook URL appear as separate string
  literals in both `app/contact/page.tsx` and `app/footer/footer.tsx`,
  rather than being imported from one `const CONTACT_EMAIL = "..."`
  source of truth.

If this site grows (more than ~3-5 pricing tiers, services, or team
members), the natural refactor is introducing exactly the kind of
`type X = {...}; const items: X[] = [...]` array-of-objects-mapped-to-JSX
pattern that's conspicuously absent today — but that's a forward-looking
recommendation, not a description of anything currently in the repo.
